# S1a D30 Rework: Vehicle-Point Alignment, LIO Frontend/Backend Split, Honest Test Counts

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement the code rework that follows from decision D30 (owner list A):
- A1: `AlignmentEstimator` measures every quantity at the vehicle position (O12) and loses its separate rate limiter;
- A2: split the single-threaded `LioEstimator` facade into `LioFrontend` (ingest thread) and `LioBackend` (estimator thread), joined by bounded queues of immutable data (O14);
- A3: `make test` deletes the selected packages' stale test results before running, and `make sanitize` also covers `uavnav_lio_core`.

**Architecture:**
- The alignment math keeps its state machine, its transition table, the PX4 reset frame change G and every public type except `AlignmentConfig`. Residual, jump gate and filter step move from the LIO origin to the vehicle point `T(p_lio)`.
- `uavnav_core` gains a header-only, lock-free, bounded single-producer/single-consumer queue.
- `uavnav_lio_core` gets:
  - `LioBackend`: owns all `fast_lio_core` math, never sees the lifecycle;
  - `LioFrontend`: owns `OutputPredictor` and `LioLifecycle`, never includes `fast_lio_core`;
  - `LioPipeline`: a synchronous driver that keeps the S1a `LioEstimator` call surface for the existing tests.
- The library still starts no thread. `LioBackend::run` is the estimator thread body that S1b's node, and this plan's threaded tests, run in a `std::jthread`.

## Review Focus

2. **The backend is stalled while IMU keeps flowing** (F22 after the split). Pinned by `SpscQueue.FullPushNeverBlocks`, `SpscQueue.ConcurrentProducerConsumerAccountsForEveryItem` (Task 3), `LioFrontend.FullRequestQueueIsAnEventAndNeverBlocks` (Task 5) and `LioPipelineThreaded.ConcurrentIngestAndBackendAccountForEveryScan` under `make sanitize` (Task 7).

## Frontend/backend design (D30/O14, §3.5)

These decisions bind Tasks 3–7. A reviewer checks code against this section.

| Topic | Decision |
|---|---|
| Queue type | `uavnav::concurrency::SpscQueue<T, Capacity>`, header-only in `uavnav_core`: a fixed ring, lock-free, never allocates, `try_push` never blocks. A full push returns `QueueError::kFull`, leaves the item untouched and counts it. The queue emits no events; the side that pushes emits one with a reason. |
| Who owns the queues | `LioChannels { RequestQueue requests; ResultQueue results; }`, owned by the object that owns both blocks: `LioPipeline` here, the `lio` node in S1b. The frontend only pushes `requests` and pops `results`; the backend does the opposite. |
| Frontend → backend | `BackendRequest = std::variant<ImuInput, ScanJob, RestartCommand>` in **one** FIFO. Every IMU copy that a scan or restart needs is therefore already queued ahead of it, so the backend never needs a cross-queue wait. |
| Backend → frontend | `BackendResult` has a kind:<br>• the §3.5 lifecycle kinds `kScanGood`, `kScanDegenerate`, `kScanEmpty`, `kMapReady`, `kRestartSeeded`;<br>• three non-lifecycle kinds `kImuInitialized` (aligns the predictor), `kScanNotProcessed` (accounting) and `kRestartRejected`.<br>It also carries `EstimatorSnapshot`, `DegeneracyReport`, the position sigma and the base_link odometry with its covariance. It never carries a `LioState`. |
| Queued scans behind a slow backend | At most `limits::kMaxScansInFlight = 2` scans that were admitted but have no result yet. A third is **refused (drop-newest)** with `EstimatorReason::kBackendBusy` and a rate-limited `LioInputRejected` event.<br>Why: the producer of an SPSC ring cannot remove an item already queued, and the ESKF must see scans in time order. Two scans means one in ICP plus one waiting at most one ICP time (20–50 ms, §3.5), so the waiting scan's correction still lands inside the 300 ms predictor buffer (§3.3). Refusing a third only happens once the backend is more than a scan period behind. |
| Full request queue | The IMU sample is still processed by the frontend (predictor, gap check, outputs). Only its copy for the backend is dropped, with a rate-limited `LioQueueOverflow` event (`kRequestQueueFull`). The backend then sees an IMU gap, so that scan's prediction fails, the ESKF is rebased and the scan is degenerate: fail closed. `limits::kBackendRequestCapacity = 512` is about 2.4 s of 200 Hz IMU plus scans, more than 4× the beta `lifecycle_gap_lost_s`. |
| Full result queue | Cannot happen by construction. Pending results are at most 2 scans + 1 restart + 1 IMU init, `kBackendResultCapacity = 8`, enforced by a `static_assert`. The backend still handles `kFull` by failing closed: `LioQueueOverflow` (`kResultQueueFull`) and the result is dropped. |
| Scan-ahead invariant | Enforced by the **frontend** at admission: `kScanAheadOfImu`, nothing changes. Every admitted scan end is ≤ the newest IMU time at admission, so every result time, and the lifecycle's last-scan time, is ≤ IMU time. The backend never sees a scan ahead of its IMU copies because the FIFO delivers them first. |
| Gap semantics (F22) | `kImuTick` runs on **every** accepted IMU sample in the frontend. The lifecycle's last-scan time advances only when a scan **result** is applied; its time is the scan end in sensor time. Dropped, unprocessed and discarded scans do not count. Backend latency therefore adds to the measured gap (≤ 50 ms at beta, inside the 0.25 s threshold), and a stalled backend reads as a LiDAR gap: no corrections means DEGRADED/LOST. |
| Matching results to the predictor | `snapshot.t` is the scan end. `OutputPredictor::on_correction` looks the buffered output up **by that timestamp** (S1a rule). A result older than 300 ms is rejected (`PredictorCorrectionRejected`, `kOlderThanBuffer`), and the lifecycle still counts the scan. |
| IMU initialisation | Backend: `ImuInitializer` on the IMU copies, then a `kImuInitialized` result carrying the snapshot at the initialising sample. The frontend aligns the predictor on it. In the synchronous pipeline this happens in the same `push_imu` call, exactly as in S1a. |
| Map policy | `ScanJob::map_policy` (`kInsert` when the lifecycle at admission is INITIALIZING/TRACKING/DEGRADED, `kFrozen` when LOST/RESTARTING) replaces S1a's read of the lifecycle inside `process()`. Bootstrap uses `map_points == 0`. |
| Restart | 1. `LioFrontend::restart(seed)`: requires RESTARTING, an aligned predictor and no pending restart. It queues `RestartCommand{new_epoch, t = newest IMU, seed, predictor latest q/v}` and tags later scans with the new epoch.<br>2. The backend clears the map, seeds the ESKF at `t` and answers `kRestartSeeded` with the snapshot at `t`.<br>3. The frontend then applies `reset_to(snapshot)`, which matches `t` in the buffer and shifts it without a rewind, switches `epoch`, feeds `kRestartSeeded` to the lifecycle, emits `LioRestart` and returns the `ResetDelta` in `StepOutputs::restart`.<br>Results whose epoch differs from the newest requested epoch are discarded (`LioResultDiscarded`, `kStaleEpoch`). |
| Synchronous driver | `LioBackend::step(now)` processes at most one request. `LioPipeline` calls the frontend, pumps `step` until it returns false, then `LioFrontend::poll_results`. This is deterministic and single-threaded, and it keeps the S1a outputs call by call. |
| OpenMP | `limits::kIcpThreads = 3` is passed to `fl::ResidualBuilderConfig::parallel_thread_count` inside `LioBackend` only. The libgomp team runs only inside the backend's correction call. Under the TSan build it is 1, because libgomp is not TSan-instrumented (GCC PR 55561). |
| Shutdown | The owner calls `request_stop()` on the backend `jthread`. `run` returns after the request in progress and leaves the rest of the queue unprocessed. Join the thread before destroying the backend, then the frontend, then `LioChannels`. |

  Every other public declaration in `alignment.hpp` is unchanged.

- **Vehicle point.** For a pair `(p_lio, yaw_lio)` with PX4 `(p_px4, yaw_px4)` interpolated at the scan time and a reference T (filtered T in VALID, accumulation mean in INIT): `q = T(p_lio) = (Rz(yaw_T)·p_lio_xy + t_xy, p_lio_z + t_z)`, `e = p_px4 − q`, `residual_position_m = |e|` (3-D), `residual_yaw_rad = wrap(yaw_inst − yaw_T)` (unchanged).
- **Jump gate:** `kPairRejectedJump`, T unchanged, when `|e| > jump_position_m` or `|residual_yaw_rad| > jump_yaw_rad` (strict, as today).
- **Filter step (VALID):** `alpha = dt/tau` (dt clamped as today); T ← G(T) through the existing `frame_change` helper with pivot `q`, shift `alpha·e`, rotation `dh = alpha·residual_yaw_rad`. So `yaw_T += dh`, `t ← Rz(dh)(t − q) + q + alpha·e`, hence `T'(p_lio) = q + alpha·e`: a pure yaw step does not move the vehicle point.
- **INIT accumulation:** members store `(inst, p_lio, p_px4)`. Mean yaw = circular mean of `inst.yaw`; mean translation = `mean(p_px4_xy) − Rz(mean_yaw)·mean(p_lio_xy)` and `mean(p_px4_z − p_lio_z)` (least squares given the mean yaw). The arrival check and the final re-check measure each member at its **own** vehicle point. With `p_lio = 0` every rule reduces to S1a's, so the boundary tests built on `LioOrigin` keep their numbers.
- **Implied rate bound:** per step at most `jump_position_m·dt/tau` of vehicle-point motion and `jump_yaw_rad·dt/tau` of yaw: 0.25 m/s and 2.5°/s at beta (§4.1).
- **Output fields** (document in `alignment.hpp`; this is what the S1b node publishes, `Alignment.msg` unchanged): `x_m`..`yaw_rad` ← `filtered`, the same `lio_odom FRD → PX4 NED` transform as before (INIT: accumulation mean, not usable); `raw_*` ← `raw`, the instant T of this call's pair; `residual_*` ← measured at the vehicle point of the newest formed pair against the reference **before** the step; `age_s`, `stamp` unchanged. The header must say that `raw − filtered` translation includes the lever arm `(Rz(yaw_raw) − Rz(yaw_filtered))·p_lio` and is not a residual.

  ```cpp
  enum class QueueError : std::uint8_t { kFull };
  constexpr std::string_view to_string(QueueError);                       // "FULL"
  struct QueueStats { std::uint64_t pushed, popped, rejected; };          // relaxed counters, readable from any thread
  template <class T, std::size_t Capacity>                                // static_assert(Capacity >= 1), T nothrow-movable
  class SpscQueue {
   public:
    SpscQueue() noexcept;                                                 // not copyable, not movable
    Result<void, QueueError> try_push(T&& item) noexcept;                 // producer thread only; never blocks or allocates;
                                                                          // kFull leaves `item` unmoved and counts `rejected`
    std::optional<T> try_pop() noexcept;                                  // consumer thread only
    void wait_nonempty(const std::stop_token& stop) const noexcept;       // consumer only; returns when non-empty or stop requested
    QueueStats stats() const noexcept;
    static constexpr std::size_t capacity() noexcept { return Capacity; }
  };
  ```

- Memory ordering: the producer writes the slot, then publishes the tail with `release`; the consumer reads it with `acquire`; the head likewise in the other direction; head and tail on separate cache lines. `wait_nonempty` uses `std::atomic::wait` on a counter that each push bumps and `notify_one`s (never blocks) and that a `std::stop_callback` bumps and notifies.

  ```cpp
    static Result<std::unique_ptr<LioPipeline>, config::ConfigError> create(const LioConfig&,
        const Eigen::Isometry3d& base_T_imu, const Eigen::Isometry3d& imu_T_lidar, events::EventRecorder&);

    Result<ResetDelta, EstimatorReason> restart(const SeedPose&, const time::TimeSnapshot& now);

    const LioFrontend& frontend() const noexcept; const LioBackend& backend() const noexcept;
  };
  ```

- Every call: the frontend call (an error is returned as is), then `backend.step(now)` until it returns false, then `frontend.poll_results(now)` merged into the outputs (states appended; a later non-empty optional replaces an earlier one).
- `restart` returns `*outputs.restart`, so the `ResetDelta` comes back in the same call as in S1a. The pipeline owns `LioChannels`, the backend and the frontend, and declares them in that order.
