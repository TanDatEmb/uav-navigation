# O3 requested Hold protocol observations

The six captured Hold episodes are C and W1–W5. Each has one local `HOLD_REQUEST` and one `SCHEDULE_ATTEMPT` (attempt generation 1), one raw `VEHICLE_CMD_SET_NAV_STATE=100001` with `param1=4` on `/fmu/in/vehicle_command_mode_executor`, a later raw ACK with result 0, and an adapter `VehicleStatus` observation of `AUTO_LOITER=4`. The first post-request AUTO_LOITER receive times were C **70.544 s**, W1 **70.156 s**, W2 **20.920 s**, W3 **25.188 s**, W4 **20.728 s**, W5 **26.144 s** in the respective ROS simulation clocks. Source stamps and observer stamps remain distinct in `O3_HOLD_PROTOCOL_EVENTS.csv`.

The audit stream records retry ticks while `pending && !confirmed`: C **1**, W1 **0**, W2 **1**, W3 **5**, W4 **0**, W5 **1**. It records **zero Hold callback (`phase=4`) events** in these episodes. The raw `/fmu/out/mode_completed` events that were present named nav state **26** (C) or **17** (W2–W5), not LOITER 4. No `ModeCompleted(LOITER)` is inferred from the ACK or the status. These exact events support the distinction between request, command ACK, callback completion, and fresh status. The ACK result is a PX4 command response, not proof of a sustained Hold state; the later `VehicleStatus` is the observed mode witness.

W3 and W5 include one `EXECUTOR_DEACTIVATE` audit event with `outcome=2` (`mode_exit`) **before the stale-world fault and before the requested Hold**. Their later executor activation/request cycle must be kept separate. They are not operator takeover evidence. No repeat Hold request, already-active Hold request, controlled pilot takeover or deterministic failsafe takeover was exercised by this harness. In particular, absence of a LOITER callback in six runs does not prove it can never arrive under the pinned dependency/PX4 firmware. The source-derived retry hazard remains conditional: `onPx4HoldHandoverCompleted(Success or Deactivated)` clears pending/in-flight even when `px4_hold_confirmed_` is false, whereas `checkHoldHandover()` only retries when pending and unconfirmed. This particular callback-before-status ordering was not reproduced.

The record preserves the existing flags on every audit event: pending, in-flight, confirmed, navigation-failure request, failsafe and operator takeover status bits; raw PX4 command, ACK, mode completion, and VehicleStatus are separate rows. A fresh status predicate for future authority transfer must be specified and tested before migration. The current diagnostic stream can represent `HOLD_UNCONFIRMED` without inventing a successful handover.
