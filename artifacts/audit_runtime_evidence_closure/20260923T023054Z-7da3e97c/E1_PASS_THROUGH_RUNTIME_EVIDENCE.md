# E1 — PASS_THROUGH runtime reachability

**Runtime verdict: `REACHABLE_BY_TRACE_BUT_NOT_FAILED`; closure verdict: `E1_PARTIAL`.** This means producer-side command ordering and physical in-ball observation occurred in one TARGET run. It does **not** prove that MissionController sampled the exact t0/t1 callback pair or that a waypoint was lost.

`FACT_FROM_PINNED_PRODUCT_SOURCE` `navigation_mode_node.cpp:1378-1409` forms an exact MAIN continuation only from an admitted, fresh command with matching mission/waypoint/request; `mission_controller.cpp:367-371,451-477,569-579` pairs current/previous measured position with that same-update continuation. `RouteProgress` and acceptance geometry are in `route_progress.cpp:254-345,430-490`. `MissionController` stores callback time for the gap, so the offline source-time replay is a **crossing opportunity**, not an exact product callback emulation. The command callback can also call `update` (`navigation_mode_node.cpp:1328-1335`), which is why a timer-only race claim would overstate evidence.

`FACT_FROM_RUNTIME_TRACE` Fourteen exact-TARGET runs yielded 32 distinct replayed PASS waypoint episodes with observed later acceptance. Twenty-eight first physical observations had an exact, unexpired MAIN continuation already published; three waypoint-zero episodes used the source-defined initial handoff exception and had no compatible continuation at first observation. One episode, run `external-mode-gui-20260922T015008-233245`, waypoint 3/request 6/epoch `90695073308889`, had 33 sequential in-ball odometry observations with latest compatible published continuation=false before a later true command. Do **not** count these 33 samples as 33 independent crossings.

For that episode, monitor source odometry first entered the 0.8 m ball at **95.732 s**, sequence retained in `E1_PASS_THROUGH_TIMELINE.csv`, speed 0.954 m/s, error 0.799 m; latest compatible command had `certified_main_continuation=0`. It remained in ball through **96.372 s**, then left. The first published true continuation has source stamp **96.971999999 s**, bundle 13/sample 2756, valid-until 97.072 s and continuation-boundary stamp 97.847647448 s. Source-time first-observation→published-readiness difference is **1.240 s**, one episode only. The next replayed in-ball observation was **97.912 s** and mission acceptance was published at **97.916 s**, error 0.793 m/speed 0.854 m/s; next goal followed at the same source stamp. The vehicle reacquired the ball, so this is **not a lost-crossing runtime failure**. Monitor and bag observer wall times have uncertain near-callback order; adapter receive and mission callback stamps are unrecorded.

`FACT_FROM_AUDIT_MODEL` The replay binary directly uses pinned `RouteProgress::update` and `measuredWaypointCrossingError` at every accepted propagated-odometry sample, applying source-time gap ≤0.25 s. Its output is an overapproximation of MissionController opportunities because product updates on its own callback schedule and uses callback gap. In 28 control episodes, first opportunity→acceptance source lag was 0–16 ms (median 8 ms); the maximum first-observation speed was 1.634 m/s and all recorded candidate gaps were 20 ms. This does not cover high-speed skipped-ball behavior or scheduling under command transport jitter.
