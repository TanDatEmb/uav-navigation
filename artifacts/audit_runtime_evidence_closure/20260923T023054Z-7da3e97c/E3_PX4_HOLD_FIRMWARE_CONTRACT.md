# E3 — PX4 Hold source contract at captured run revision

**External verdict: `BLOCKED_BY_UNPINNED_FIRMWARE`; branch verdict: `E3_BLOCKED`.** The exact run-specific firmware source/binary evidence substantially narrows the protocol, but the product does not pin firmware as a global baseline and the required protocol topics were not recorded. All firmware statements below are `FACT_FROM_PINNED_FIRMWARE` **for the captured run revision** `deaff86e…` plus captured dirty diff/binary hash in `PROVENANCE.md`, not a qualified product-wide contract.

1. `FACT_FROM_PINNED_PRODUCT_SOURCE` `navigation_mode_node.cpp:2846-2939`: `schedulePx4Hold` sets pending/in-flight then calls `scheduleMode(kModeIDLoiter)`. Freshness is absent from local `px4_hold_confirmed_`: any received `AUTO_LOITER` sets it and clears pending/in-flight. `ModeCompleted(Success)` **or** `Deactivated` callback also clears pending/in-flight without status. Failure schedules a 250 ms retry; timer checks `pending && !confirmed && !in_flight`. An ACK success with no `ModeCompleted` and no status can leave in-flight indefinitely; a callback success/deactivation without status can end retry unconfirmed.
2. `FACT_FROM_PINNED_DEPENDENCY` pinned interface library `mode_executor.cpp:125-260` sends `VEHICLE_CMD_SET_NAV_STATE`, waits for matching `VehicleCommandAck` and maps `ACCEPTED` to `Result::Success`, then activates `ScheduledMode`. `:484-519` invokes its callback only for a matching `ModeCompleted` while active or on cancel (`Deactivated`). `:361-419` separately processes `VehicleStatus`; `mode.cpp:171-188` deactivates the owned external mode when `nav_state` no longer equals its id. ACK, status, completion, and deactivation can arrive in different orders. A completion emitted before `ScheduledMode::activate` is not consumed by that operation.
3. `FACT_FROM_PINNED_FIRMWARE` captured Commander `Commander.cpp:936-946` ACKs the command when `_user_mode_intention.change` accepts the requested state; it does not wait for observed `nav_state`. `:1565-1593` forwards executor commands only if its source matches `modeExecutorInCharge`. `:2367-2373` computes actual `nav_state` after failsafe selection and publishes `executor_in_charge` in the same status update. `ModeManagement.cpp:415-435` resets charge to autopilot on a **user** switch to a non-owned mode; a mode-executor switch to non-owned `AUTO_LOITER` may retain executor charge. `Navigator::run` selects `_loiter` for `AUTO_LOITER` (`navigator_main.cpp:768-783`). `Loiter::on_activation/on_active` maintain the persistent loiter setpoint (`loiter.cpp:51-74`). The `mode_completed` producer (`navigator_main.cpp:1602-1608`) is called from finite navigator modes (takeoff, land, mission, RTL); source search found no call in `loiter.cpp`. Thus persistent Loiter may never emit `ModeCompleted(LOITER)`.

**Correction to V2 candidate:** requiring `executor_in_charge` to become autopilot for successful requested Hold is too strict for this captured firmware. A fresh, post-request PX4 `AUTO_LOITER` status is the minimal mode-occupancy witness; `executor_in_charge=1` may coexist. The word “authority” must distinguish PX4 flight-mode/setpoint selection from executor scheduling right. The source does not prove a safe retry deadline or how to distinguish a coincident pilot LOITER selection from the request without a correlated command/status sequence.

H-Q1: fresh, monotone post-request `VehicleStatus.AUTO_LOITER`, with request/observation attribution. H-Q2: the same fresh status proves external nav mode not active and PX4 Navigator selects Loiter; adapter deactivation of the owned mode is a separate local witness that its timer stopped. H-Q3: yes, source stamp/receive freshness and post-request sequence are required; current boolean lacks them. H-Q4: absent completion must not itself block confirmation from status or silently end retry; current in-flight behavior can. H-Q5: `Deactivated` is cancellation, cause unresolved without status/deactivation reason. H-Q6: confirmed pilot/failsafe takeover should terminate retry as an **external takeover** outcome, not requested-Hold success; policy owner must approve exact override.

`EXTERNAL_CONTRACT_UNRESOLVED`: product-level firmware pin/build, causal request→status correlation under competing pilot/failsafe changes, status freshness bound, and safe bounded retry on missing callback/status. Do not derive them from an API name or a cached boolean.
