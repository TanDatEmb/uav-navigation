# O2 — command identity and timing

**Verdict: `O2_REQUIRES_INSTRUMENTATION`; exact publish→receive paired samples: 0.** `FACT_FROM_TARGET_CODE` `sample_id` is advanced by checked monotonic `advanceMonotonicId` (`navigation_runtime_node.cpp:8391-8403`, `runtime_boundaries.hpp:79-90`), with fail-closed overflow. Within one confirmed producer incarnation the minimal key is `sample_id`; cross-incarnation use requires an actual producer/process incarnation ID plus `sample_id`. A runner session ID alone cannot prove uniqueness across an in-run runtime-node restart. The offline join uses `(runner runtime_instance_id, localization_epoch, goal_epoch, request_id, bundle_generation, sample_id)`. The runner's runtime instance ID is a session annotation (`external_mode_scenario.py:354-355`), **not a NavigationCommand field**. A future recorder must supply run/process incarnation. Identity changes at bundle/goal/localization boundaries do not create collisions in these runs; 83,453 command keys have zero duplicates, and all 68,936 first tracking uses plus reused tracking trace rows matched one key. This verifies this dataset, not future global uniqueness.

`FACT_FROM_TARGET_CODE` `execution_authorization_steady_ns` is sampled before `command_publisher_->publish` (`navigation_runtime_node.cpp:8559-8565,8669-8683`). Adapter `px4_input_trace.update_start_steady_ns` is set just before `trajectory_setpoint_->update` (`navigation_mode_node.cpp:2782-2793`). Both call the same host `std::chrono::steady_clock` helper (`navigation_common/time.hpp:33-38`). Consequently `T_first_setpoint_start − T_authorization` is a **causal upper envelope** on time from authorization through publication, DDS delivery, adapter acceptance and scheduling to first setpoint. It is neither direct transport latency nor a proof of the 100 ms receive lease margin. `last_command_receive_ns_` is set on adapter acceptance in ROS clock at `navigation_mode_node.cpp:1131-1144`; it is not emitted with command identity. The adapter checks receive lease and separate source/valid-until conditions at `:2639-2662`.

`FACT_FROM_EXISTING_RUNTIME_ARTIFACT` `O2_COMMAND_LATENCY.csv` reports each run separately. Across **heterogeneous** profiles, 68,936 first tracking uses have zero negative clock pairs and zero authorization→first-use age ≥100 ms. Per-run maxima range up to **20.345 ms** (`...241674`); in the long multiwaypoint run `...247206`, N=14,560, p50=8.027 ms, p95≈8.14 ms, p99=8.225 ms, max=10.424 ms. The first-use upper envelope is a useful observed margin **during emitted tracking uses**. It excludes commands never used, receive callbacks that rejected them, standby/velocity-hold gaps and mode handovers. Reused setpoint rows can exceed 100 ms from the old *authorization* (three rows across runs), which is not a measured receive-lease violation. Recorder/setpoint interarrival gaps ≥100 ms include phase transitions and one infrastructure-invalid simulation pause; they must not be relabeled lease failures. The prior single-run recorder command interarrival p99=20.508/max=40.510 ms is observer timing, not adapter receipt.

Minimum missing pair: exact same command's steady `publish_enter`/`publish_return` and adapter callback entry/accept or reject steady stamp. Required stage metrics `publish→receive`, `receive→setpoint`, and adapter receive interarrival are `UNOBSERVABLE_WITH_CURRENT_TARGET`; all corresponding p50/p95/p99/max and actual `>=100 ms` lease-violation count are **N/A**, not zero. Source/ROS, host steady, runner observer and PX4 boot times are never mixed. A one-run p99 or all first-use upper envelopes cannot establish a worst credible scheduling/DDS tail under pauses and load. Healthy current runtime provides observed first-use headroom in the captured tracking portions, but the 100 ms receive-lease contract is not closed.
